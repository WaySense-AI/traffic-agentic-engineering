# 第九章 工程验证：从生成结果到可信决策

## 9.1 为何验证定义了工程

工程与对话式智能有着根本区别，而这一区别凝聚在一个词上：**验证（validation）**。

语言模型可以生成令人信服的解释、看似合理的计算或优雅的建议。它可以产出读起来仿佛出自经验丰富的工程师之手的文本。它甚至可能在大多数时候是正确的。然而，工程判断一个结果的标准，不在于它听起来多么有说服力、语气多么自信或使用了多少技术术语。工程判断一个结果的标准在于它是否满足**客观约束、工程标准、物理定律和可测量的证据**。

正因如此，验证不是一个附加步骤——一个 bolt 在生成过程末端的质量门。**它是工程本身的定义性特征。** 一个进行验证的学科是工程；一个仅仅生成的学科是别的什么。无法被验证的建议无法被交付。未经验证的交付产物不是工程——它是披着技术语言外衣的意见。

这一原则对 TAE 架构具有深远的架构意义。框架中的每一个组件——从责任模型到推理规划器到原语依赖图——的存在都是为了服务于产出可被验证的输出。如果将验证从架构中移除，剩余组件仍能运行，但它们不再构成一个*工程*系统。它们将是一个具备领域知识的精良内容生成器。

> **验证原则**：在工程中，未验证的输出不仅仅是不完整的——它是不存在的。一份未核实的信号配时方案根本不是配时方案；它是一个等待确认的假设。验证不是工程的最后一步；它是*创造*工程输出的那一步。

## 9.2 验证是工程责任

交通工程不会在分析完成后便告终结。每一项工程结论在被接受投入运营使用之前都必须经过审查。不同于依赖满足用户即时好奇心的貌似合理答案的通用对话系统，工程系统在一个更严格、要求更高的制度下运行：**每项建议在付诸实施之前必须满足工程标准、运营约束和实际可行性**。

TAE 因此将工程验证视为工程推理的一个**组成部分**，而非事后附加的最终检查步骤。这种整合带来了几项重要后果：

- **验证感知的推理**：推理规划器（第五章）不只是生成假设；它生成的是*可验证的*假设——能够收集证据、检查约束、核实结果的假设。
- **验证引导的原语选择**：工程原语（第六章）的选择受其验证属性影响。产生不透明、不可复现结果的原语，其价值低于输出可被独立验证的原语。
- **验证结构化的交付**：产物模板（第八章）包含专门的验证证据章节，而非作为附录而是作为文档的核心组件。

通过将验证嵌入架构各处而非将其降级为事后检查，TAE 确保工程质量是内建的，而非外检的。

## 9.3 生成容易，责任难

现代基础模型大幅降低了生成工程内容的成本。报告、信号配时方案、仿真脚本和优化策略都可以自动生成，流畅度和表面能力令人印象深刻。这种能力虽然令人瞩目，却制造了一种危险的错觉：**生成即正确的错觉**。

考虑以下仅靠生成本身无法防止的失败模式：

| 生成输出 | 潜在失败 | 为何生成无法捕捉 |
|---------|---------|----------------|
| 优化后的信号配时方案 | 违反行人最小绿灯时间 | 生成器不知道本地约束 |
| 协调策略 | 超出交叉口间可行 offset 范围 | 生成器忽略物理几何 |
| 拥堵诊断 | 未考虑上游溢出 | 生成器缺乏网络上下文 |
| 仿真结果 | 与观测到的检测器数据矛盾 | 生成器未与真值比对 |
| 通行能力分析 | 使用不适合本地条件的饱和流率 | 生成器套用了通用默认值 |

每种情况下，生成输出可能内部一致、格式规范，甚至具有说服力。然而每种都包含熟悉具体站点及其约束的合格工程师一眼就能看出的错误。这些错误不是生成的失败；它们是**验证**的失败。

TAE因此在**生成结果**与**经过验证的工程决策**之间划出清晰界限：

- **生成结果**：推理系统产出的输出。它可能正确也可能不正确。其状态是暂时的。
- **经过验证的工程决策**：通过了所有适用验证层（第 9.7–9.11 节）的生成结果。其状态是确认的。只有经过验证的决策才能履行工程责任。

这一区分并非语义学究。它决定了系统被允许交付什么。未验证的结果保留在推理过程内部；只有经过验证的决策才能跨越交付门槛（第八章）。

## 9.4 验证不止于核实

两个常被混淆的概念之间存在微妙但重要的区分：**核实（verification）**与**验证（validation）**。

- **核实**问：*计算是否正确执行？* Webster 公式是否收到了正确输入？算术是否无误？输出是否在给定输入下符合预期？
- **验证**问：*工程结论对现实世界的情况是否适当？* 即使计算正确执行，结论是否真正解决了问题？实施后能否奏效？

考虑这个例子：一份信号配时方案满足所有数学约束——最小绿灯时间达标、周期时长在范围内、绿信比加和正确、offset 可行。计算已被**核实**。然而，当以实际交通需求模式仿真运行时，该方案在关键进口道产生的排队比现有配时更长。该工程决策**未被验证**——尽管计算上完全正确。

核实/验证的区分清晰地映射到 Boehm 推广的软件工程术语：
- **核实**："我们是否在正确地构建产品？"（执行的正确性）
- **验证**："我们是否在构建正确的产品？"（结果的适当性）

TAE 二者皆需。核实确保计算完整性；验证确保工程相关性。只做核实的系统对可能错误的问题给出正确答案。只做验证的系统产出建立在脆弱基础上的潜在有用答案。工程二者缺一不可。

## 9.5 工程验证金字塔

交通工程验证发生在多个层级，每层应对不同类别的工程风险。这些层级形成一个层级结构——**验证金字塔**——其中高层依赖于低层，跳过任何一层都会损害整个验证努力。

```
          ┌─────────────────────┐
          │  Level 5: Review    │ ← 人类判断
          │  Engineering Review │   (特殊案例)
         ┌┴─────────────────────┴┐
         │  Level 4: Simulation │ ← 假设检验
         │  Simulation Validation│   (复杂系统)
        ┌┴───────────────────────┴┐
        │  Level 3: Calculation  │ ← 可复现性
        │  Calculation Validation│   (确定性数学)
       ┌┴─────────────────────────┴┐
       │  Level 2: Constraint      │ ← 规则合规
       │  Constraint Validation    │   (法规)
      ┌┴───────────────────────────┴┐
      │  Level 1: Syntax           ← 结构完整性
      │  Syntax Validation         │   (格式/结构)
      └───────────────────────────┘
```

一项建议只有在通过每个适用的验证层之后才值得信赖。两条原则支配着金字塔的遍历：

1. **跳过高层增加工程风险。** 一份通过了语法和约束检查但从未被仿真的信号配时方案带有未知风险。
2. **跳过低层使高层验证变得无意义。** 对格式错误的产物（第一层失败）进行工程评审（第五层），是在本应被自动捕获的问题上浪费专家时间。

并非每种产物都需要全部五级。常规排队长度估计可能只需第一至三级。复杂走廊的新型协调策略应通过全部五级。RCC（第 8.3 节）规定了每种责任类型适用哪些级别。

## 9.6 多维验证范围

除了层级金字塔之外，工程验证还在多个**维度**上运作——工程输出的不同方面各自需要验证：

### 原语验证

每个工程原语必须产出技术上正确的结果。通行能力计算必须使用正确公式。排队估计必须尊重物理限制。延误分析必须应用适当方法论。原语验证是基础——如果单个原语产出垃圾，整个推理链都会受损。

### 推理验证

推理过程本身必须遵循公认的交通工程原则。原语之间的依赖关系必须在逻辑上可靠（如依赖图第七章所规定）。假设必须显式且有据可依。从观测到结论的推断链必须保持连贯且可追溯。推理验证捕捉的是工程师*如何思考*中的错误，而不只是*计算了什么*的错误。

### 策略验证

所选工程策略必须与评估的交通状况相匹配。为经常性拥堵设计的策略（如重新配时）不应应用于事件引发的拥堵（如动态分流）。适用于孤立交叉口的解决方案在网络级问题上可能是错的。策略验证确保用对了工具做对了事。

### 交付验证

最终工程产物必须满足预期用户的需求。交通运营者需要清晰的可操作建议。工程咨询顾问需要详细的方法论文档。政府机构需要合规认证。交付验证确保 artifact 服务于其受众。

这四个维度——原语、推理、策略和交付——构成一个**验证范围矩阵**，与层级金字塔互为补充。一个完全验证过的工程输出既通过了所需的金字塔级别，又满足了所有适用的范围维度。

## 9.7 第一级——语法验证

金字塔的第一层确保工程输出是**结构完整**的。语法验证不判定一个工程决策是否正确；它仅确保该决策可以进入工程工作流而不会引发处理错误。

语法验证检查包括：

| 检查类别 | 示例 | 失败后果 |
|---------|------|---------|
| 参数完整性 | 所有必填字段均存在 | 下游计算失败 |
| 格式正确性 | 信号配时值为期望单位 | 控制器拒绝上传 |
| 结构有效性 | 相位序列物理可实现 | 实施不可能 |
| 一致性 | 各数据源坐标系对齐 | 空间分析受损 |
| 完整性 | 场景描述包含所有必需要素 | 报告被审阅者拒收 |

语法验证是最快、最机械化的层级。它可以完全自动化，应在毫秒级完成。其目的是在 trivial 错误消耗高层昂贵验证资源之前将其捕获。缺少相位时长的信号配时应被立即拒绝——而不是在完整仿真运行之后才拒。

把语法验证看作编程语言的编译器语法检查：它在尝试解释程序逻辑之前先捕获缺失的分号和不匹配的括号。同理，TAE 的语法验证在尝试评估工程内容之前先捕获缺失参数和格式错误。

## 9.8 第二级——约束验证

工程决策必须满足**工程规格**——代表法规要求、安全强制令和物理限制的规则。这些约束是不可协商的：任何强制性约束的违反都会立即使拟议方案无效，无论它在其他维度上看起来多么最优。

交通工程中的典型约束包括：

| 约束类别 | 示例 | 来源 |
|---------|------|------|
| 最小绿灯时间 | 行人清空 ≥ 7 s | MUTCD / 地方法规 |
| 最大周期时长 | 周期 ≤ 180s（或机构特定限制） | 控制器硬件 / 政策 |
| 行人清空 | 步行+清空时间充足 | ADA / 无障碍法律 |
| 相位兼容性 | 冲突流向不得同时放行 | 物理 / 安全 |
| 车道通行能力 | 设计小时 v/c 比 ≤ 1.0 | HCM 方法论 |
| 控制器实现 | 配时方案适配控制器内存/型号 | 硬件规格 |

这些约束代表的是**工程法规**，而非优化目标。它们定义了优化操作所在的可行域。一份总延误降低 20% 但违反行人最小绿灯的配时方案不是"有小瑕疵的好方案"——它是一份无法实施的无效方案。

约束验证同样完全可以自动化。每个约束表达为一个谓词（拟议方案的布尔函数），验证并发地评估所有谓词。任何返回 false 的谓词产生一条具体的错误信息，指明违反的约束、提议值和限制阈值。

## 9.9 第三级——计算验证

交通工程包含许多**确定性计算**——给定相同输入应始终产出相同输出的数学程序。这些计算构成工程分析的定量骨干，其正确性对于可信结论至关重要。

需要验证的确定性计算示例：

| 计算 | 方法论 | 关键输入 | 典型输出 |
|------|--------|---------|---------|
| 最佳周期时长 | Webster 公式 | 关键车道流量，损失时间 | C_opt (秒) |
| 饱和流率 | 车头时距测量 / HCM 默认值 | 几何条件，调整系数 | s (veh/h/ln) |
| 饱和度 | v/c 比 | 流量，通行能力，PHF | X (比值, 0–1) |
| 平均排队长度 | 确定性 / Akcelik | 流量，通行能力，信号参数 | Q (米/车辆) |
| 控制延误 | HCM 均匀 + 增量延误 | X, C， progression 因子 | d (秒/车) |
| LOS 分级 | 延误阈值（HCM 展示表） | 控制延误 | LOS (A–F) |

TAE 要求所有确定性计算都是**可复现的**。每个报告数值必须引用：
- 所使用的计算原语（如 `traffic.cycle.webster`）
- 输入参数及其来源（如"关键流量 = 420 veh/h，来自检测器 D3"）
- 计算证据（中间值，如适用）
- 适用处的不确定性估计

这一要求使工程计算变得**可审计**。任何审阅产物的工程师都应能从文档化的输入和方法论复现每一个数字。如果不能复现，要么计算错了，要么文档不足——二者都是验证失败。

## 9.10 第四级——仿真验证

有些工程决策无法仅凭方程来验证。信号协调策略、自适应配时响应、网络级优化效应以及溢出传播和死锁动态等涌现现象，必须通过**仿真**来验证——交通系统行为随时间的可执行建模。

仿真验证回答解析方法无法回答的问题：

| 问题 | 解析方法可行？ | 需要仿真？ |
|------|-------------|-----------|
| 排队长度是否下降？ | 近似（确定性排队） | 是（时间依赖动态） |
| 延误是否改善？ | 是（HCM 延误公式） | 部分（车队效应） |
| 溢出是否消失？ | 否（网络效应） | **是** |
| 通过量是否提升？ | 部分（通行能力分析） | 是（交互效应） |
| 策略是否保持稳定？ | 否（动态反馈） | **是** |

因此仿真成为**工程假设的可执行验证**。当第一至三级验证拟议方案的静态属性时，第四级验证动态行为——当交通按照现实行为模型在时空流动时方案的表现如何。

TAE 不指定特定仿真工具（VISSIM、SUMO、TransModeler、Paramics 等）。相反，它定义**仿真验证协议**：
1. 建立校准至观测条件的基线场景
2. 在仿真环境中实施方案
3. 运行多次随机重复（最少 5–10 个种子）
4. 比较前后效能指标（MOE）
5. 记录改善的统计显著性
6. 标记次要指标的任何退化

通过仿真验证的方案已经经受住了现有最严格的自动化测试。它不仅证明了内部一致性和规则合规性，更证明了在真实世界模型中的**行为有效性**。

## 9.11 第五级——工程审阅

并非每个工程问题都能完全自动化。特殊活动（马拉松、演唱会、体育赛事）、施工阶段复杂的建设项目、需要实时判断的交通事件以及具有分配后果的公共政策决策，往往需要超出当前 AI 能力的**人类判断**。

工程审阅代表验证金字塔的最高层级——不是因为数学上最复杂，而是因为它整合了难以形式化的知识形态：专业经验、情境理解、政治敏感性和伦理判断。

AI 在此层的角色因此**不是替代工程师，而是准备可供专家高效审阅、修改和批准的工程决策**。具体而言，AI 应当：
- **预验证**所有较低层级（1–4），使人工审阅者绝不浪费时间在 trivial 错误上
- **清晰地呈现证据**，使每条建议的理由一目了然
- **突出不确定性**，使审阅者知道最需要判断之处
- **接受标注**，使审阅者反馈成为永久记录的一部分
- **追踪修订**，使决策的演变得到完整文档化

当此工作流正确运转时，工程师将认知带宽用于真正困难的判断，而非捕捉算术错误或缺失的数据字段。AI 处理机械性的部分；人类处理有意义的部分。这种劳动分工不是临时权宜之计——它是工程 AI 的可持续模式。

## 9.12 验证需要独立证据

工程结论不能自我验证。一个使用得出结论的相同假设和数据来检查自身工作的推理系统，从事的是循环论证，而非验证。需要的是**独立证据**——源自推理过程之外、可以确认或反驳其输出的信息。

独立验证证据的典型来源包括：

| 证据来源 | 类型 | 独立程度 |
|---------|------|---------|
| 现场观测 | 直接测量 | 高（真值） |
| 检测器测量 | 自动传感 | 高（独立仪器） |
| 视频记录 | 视觉文档 | 中-高（不同模态） |
| 浮动车轨迹 | 探针数据 | 高（独立车队） |
| 仿真实验 | 基于模型的预测 | 中（同模型风险） |
| 历史工程案例 | 先例比较 | 中-高（时间独立性） |
| 运营绩效指标 | 实施数据 | 最高（真实世界结果） |

独立证据为确认或否决工程结论提供了客观基础。它将验证从内部一致性检查转化为外部现实检验。证据源的独立性越强，成功验证赋予的信心就越大。

TAE 要求第一级之上的每个验证层都纳入独立证据。约束检查（第二级）引用外部法规文件。计算验证（第三级）在可用时与真值观测对比。仿真验证（第四级）使用基于现场数据的校准模型。工程审阅（第五级）引入外部人类判断。在每个层级，系统都用自己未产生的信息来审视自己的结论。

## 9.13 验证是迭代过程

工程验证很少在单个周期内完成。拟议方案在测试中可能揭示新证据，从而引出修正的假设、更新的分析和替代工程策略。第一次验证尝试可能失败；第二次可能部分成功；第三次可能暴露此前隐藏的问题。这不是验证过程的缺陷——它反映了真实工程的工作方式。

考虑信号配时优化的典型多周期验证轨迹：

```
Cycle 1: 初始提案 → FAIL（违反最小绿灯）
    ↓ 修复：增加行人相位
Cycle 2: 修正提案 → PASS（约束）→ FAIL（仿真显示溢出）
    ↓ 修复：缩短周期，调整 offset
Cycle 3: 二次修正 → PASS（约束）→ PASS（仿真）→ PARTIAL（审阅者要求补充晚高峰场景）
    ↓ 扩展：添加高峰变体
Cycle 4: 最终提案 → PASS（所有层级）→ 已交付
```

每个周期产生新信息并馈入下一轮。验证因此创造了一个**反馈过程**，工程推理借此逐渐收敛到一个可靠的解。工程智能是通过持续精炼实现的，而非单次推理。

所需验证周期数取决于问题复杂度、初始方案质量和验证标准的严格程度。简单问题可能一周期解决。复杂的网络优化可能需要数十个周期。TAE 不设人为限制——循环持续运行直到所有完成条件均已满足或问题被判定为不可行。

## 9.14 工程验证循环

验证的迭代性自然引出了**工程验证循环（Engineering Validation Loop）**的概念——TAE 据此精炼工程输出直至其达到验证状态的循环过程：

```
观测
    ↓
推理（规划器 + 原语 + 依赖图）
    ↓
决策（拟议方案）
    ↓
验证（金字塔第 1–5 级）
    ↓
[通过?] ──Yes──→ 交付（第八章）
  │
  No
  ↓
修复（诊断失败，修复根因）
    ↓
再验证（返回验证步骤）
```

此循环是 TAE 的运行心跳。不同于对话式精炼——用户提供自然语言反馈（"再详细点"、"重试"）——工程验证循环由**工程证据**驱动，而非语言偏好。修复步骤不是用不同措辞重新生成文本的问题；而是识别具体验证失败、在推理链中诊断其原因并施加针对性纠正。

三个属性将工程验证循环与通用迭代精炼区分开来：

1. **证据驱动**：每次迭代由一条有文档理由的具体验证失败触发，而非主观不满。
2. **针对性**：修复直接针对识别出的失败模式，而非从头重新生成整个方案。
3. **可终止**：循环有明确的终止条件（所有验证层通过），防止无限精炼。

## 9.15 验证产出工程置信度

验证不只产出二元结果（通过/失败）。它建立的是**工程置信度**——对可用证据支持工程结论的程度所做的分级评估。

工程置信度反映多重因素：

| 因素 | 描述 | 对置信度的影响 |
|------|------|--------------|
| 证据质量 | 数据源的精度、准确度、时效性 | 更高质量 → 更高置信度 |
| 证据一致性 | 各独立证据源之间的一致性 | 一致 → 更高置信度 |
| 证据完整性 | 对所有相关方面的覆盖 | 完整 → 更高置信度 |
| 推理有效性 | 逻辑依赖的可靠性 | 有效 → 更高置信度 |
| 验证深度 | 通过的金字塔层级数 | 更深 → 更高置信度 |
| 历史追踪记录 | 类似过往验证的结果 | 成功历史 → 更高置信度 |

工程置信度使决策者不仅能了解*推荐了什么*，还能了解该建议获得支持的*强度*。高置信度建议（如"周期从 140s 缩短至 120s，经 10 个随机种子的验证仿真支持，延误降低 15%"）值得立即实施。低置信度建议（如"考虑增设保护左转相位，经碰撞模式分析支持但尚未经仿真验证"）值得在行动前进一步研究。

这种精细的输出——带置信度分级的建议——正是工程智能与二元分类的区别所在。真实工程决策是在不确定性下做出的，诚实地传达这种不确定性是对负责任实践的必要条件。

## 9.16 验证创造工程知识

每一次验证活动都创造新的工程知识，不论其结果如何。这或许是验证体系中最被低估的一面。

**成功的验证**强化既有工程策略。当一份拟议配时方案通过全部五级验证时，系统学到此类策略对此类问题有效。经验证的方法成为未来类似责任的模板。

**失败的验证**揭示局限、缺失证据或错误假设。当拥堵诊断因上游溢出建模不充分而未通过仿真验证时，系统学到网络上下文比最初假定的更重要。失败标识了推理过程中应在未来迭代中弥补的缺口。

两种结果都对工程智能的持续演进有所贡献。TAE 因此将验证视为一种**组织学习**机制，而非仅仅是质量保证。每个验证周期提升系统在后续周期中的能力——不是通过参数更新（如机器学习训练那样），而是通过积累经验证的工程资产、精炼的模板和文档化的失败模式。

| 验证结果 | 产生的知识 | 未来价值 |
|---------|----------|---------|
| 通过（完整） | 经证实的策略模板 | 可复用的方法 |
| 通过（部分） | 已知局限 | 风险意识 |
| 失败（约束） | 边界条件 | 更好的约束建模 |
| 失败（计算） | 方法论缺口 | 改进的原语 |
| 失败（仿真） | 遗漏的动态效应 | 增强的场景覆盖 |
| 失败（审阅） | 识别人因 | 更好的审阅者支持 |

## 9.17 验证建立工程信任

信任无法 prompt 出来。它不能通过更长的推理链、更大的语言模型或更精巧的 prompt engineering 来生成。信任不是生成过程的属性——它是验证过程的属性。

**工程信任通过成功的验证来积累。**

每次完成的验证都成为新的工程证据。每次验证通过的交付都成为可复用的工程资产。每次捕获的错误都展示了对质量的承诺。久而久之，这些积累会复合放大：反复从 TAE 系统收到经过验证、可操作产物的工程师，会对系统的输出产生信任。这种信任是赢得的，不是宣称的。

反之亦然。一次高调的验证失败——一份导致死锁的已交付信号配时方案、一份遗漏关键安全问题的诊断——可以摧毁数月乃至数年建立的信任。验证金字塔的存在不仅是为了保证当前质量，更是为了保护使未来人机工程协作成为可能的累积信任资本。

TAE 因此衡量工程智能**依据的不是生成能力，而是经过验证的工程责任履行**。生成精彩但验证糟糕的智能体是危险的。生成平实但验证严格的智能体是有价值的。

## 9.18 验证闭合工程循环

交通工程本质上是一门闭环学科。观测导向评估。评估定义责任。责任指引策略。策略产生推理。推理生成决策。**验证决定这些决策应被接受、修改还是拒绝。**

工程验证闭合了工程循环，确保工程智能保持可信、可解释且持续改进。没有验证，循环是开放的：推理产生的决策流入世界却未经检验，也不存在从结果学习的机制。有了验证，循环是闭合的：每个决策都被检验，每次检验都产生学习，每次学习都改善未来的决策。

这种闭合是 Volume I 的概念收官。让我们追溯完整链条：

| 章节 | 组件 | 链条中的角色 |
|------|------|------------|
| Ch. 3 | 责任 | 定义*什么*需要做 |
| Ch. 4 | 工程 IR | 规定*什么*是方案所需要的 |
| Ch. 5 | 推理规划器 | 确定*如何*对其进行推理 |
| Ch. 6 | 工程原语 | 提供推理的*原子单元* |
| Ch. 7 | 依赖图 | 将原语组织成*推理结构* |
| Ch. 8 | 交付 | 从推理中产出 *artifact* |
| **Ch. 9** | **验证** | **确保 artifact *可信*** |

Volume I 建立了交通智能体工程的理论基础：从工程责任到验证交付的完整链条。Volume II 将探讨这一基础如何在规模上落地运营——通过领域编译器、多智能体协调、组织工程记忆以及在真实交通机构中部署 TAE 的实际挑战。

## 第九章小结

未经验证的工程推理不可信赖。TAE 将工程验证整合到工程工作的每个阶段，从单个原语到最终工程产物。通过将工程决策锚定于独立证据、工程标准和迭代精炼，验证将工程推理转化为可靠的工程智能。

本章确立的核心原则如下：

1. **验证定义工程**：未验证的输出不是工程输出。
2. **生成 ≠ 正确性**：基础模型生成容易；工程责任难。
3. **核实 ≠ 验证**：计算正确性不蕴含工程适当性。
4. **五级金字塔**：语法 → 约束 → 计算 → 仿真 → 审阅。
5. **多维范围**：原语、推理、策略、交付四维验证。
6. **独立证据**：验证需要外部真值，而非内部一致性。
7. **迭代循环**：观测 → 推理 → 决策 → 验证 → 修复 → 再验证。
8. **置信度分级**：非二元通过/失败，而是精细的工程置信度。
9. **组织学习**：成功和失败都产生工程知识。
10. **信任积累**：信任通过反复成功验证来赢得。

**验证是推理与可信工程执行之间的桥梁。**
